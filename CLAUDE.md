# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a **.NET 10 ASP.NET Core app (`Microsoft.NET.Sdk.Web`) hosting Blazor Server plus background worker services**, run as a **plain console executable in one of two modes** (foreground or detached background — see below; it is **no longer a Windows Service**). It started life as a Worker Service template and was converted: the same process serves an interactive Blazor Server UI *and* runs the scheduler/watchers as hosted background services.

## Commands

Run from the repo root (`C:\Projects\BackupService`). The solution is `BackupService.slnx` (the newer XML solution format); the project lives in `BackupService/`.

```powershell
dotnet build                          # build the solution
dotnet run --project BackupService    # run web host + worker (Ctrl+C to stop)
dotnet watch --project BackupService run   # run with hot reload
```

Running interactively (console / `dotnet run`) starts Kestrel and serves the Blazor UI. To run the deployed exe, use one of the two run modes (see "Run modes" below).

**HTTP only — deployed on `http://localhost:55000`, dev on `http://localhost:5080`.** There is no HTTPS (the admin UI is local-only). The port lives in **environment-specific** config (not base `appsettings.json`): `appsettings.Production.json` → `Kestrel:Endpoints:Http:Url` = 55000 (a deployed run has `ASPNETCORE_ENVIRONMENT` unset → Production), `appsettings.Development.json` → 5080. Base `appsettings.json` intentionally has **no** `Kestrel:Endpoints` — otherwise Visual Studio reads it as the default and launches the browser on 55000 even in debug. The dev launch profile (`launchSettings.json`) sets `ASPNETCORE_ENVIRONMENT=Development` (web-standard) and `applicationUrl=5080`. Note a `Kestrel:Endpoints` value takes precedence over `ASPNETCORE_URLS`/`applicationUrl`, so the per-environment port is set via the config layer.

**Run modes (`Hosting/`):** the exe parses its command line (`ApplicationModeParser`) into one of three behaviours:
- **no args → foreground:** runs the host attached to the terminal; all `ILogger`/console output goes to the terminal, Ctrl+C stops it.
- **`-background` / `-bg` → background:** relaunches the exe as a **detached `--worker` child** (`BackgroundProcessManager.LaunchDetached` — `CreateNoWindow`, working dir = exe dir) and returns immediately printing the child PID. The child has no terminal, so it points `Console.Out`/`Console.Error` at a **`DailyRollingLogWriter`** that writes `{data dir}\logs\backupservice-{yyyy-MM-dd}.log` (one file per local day, auto-flushed) with **14-day retention** (purged on start + each daily roll; `SelectExpiredLogFiles` is the pure, unit-tested core).
- **`-stop` → stop:** sets a named stop event (`BackgroundProcessManager.RequestStop`) that the running host waits on (registered via `RegisterStopSignal(app.Lifetime)` → `IHostApplicationLifetime.StopApplication()`), then waits on the PID file for the process to exit. A no-op stop (nothing running) is not an error.

A **single-instance guard** (a per-session `Local\` named `Mutex` in `BackgroundProcessManager`) makes a second launch (foreground or background) exit with "Backup Service is already running." instead of a Kestrel bind failure; the names are per-session, so each interactive Windows user runs an independent instance. The host pins **`ContentRootPath = AppContext.BaseDirectory`** (the old `UseWindowsService()` used to do this) so `appsettings.json`/the Kestrel binding are found regardless of the launching working directory. A `{data dir}\backupservice.pid` file is written on start and deleted on graceful exit. **Future (not built):** a Settings option to start the app on Windows logon (it would register the exe with `-background`).

**Deploy via publish profile:** `Properties/PublishProfiles/Install.pubxml` publishes to `C:\Tools\BackupService` — `dotnet publish -p:PublishProfile=Install`. A **pre-publish** target runs `BackupService.exe -stop` (ignored if nothing is running) so files aren't locked during the copy; there is **no** service-install step. After publishing, start it with `C:\Tools\BackupService\BackupService.exe -background` (stop with `-stop`). **One-time migration:** a build deployed before this change ran as a Windows Service — remove that leftover service once with an elevated `BackupService.exe --uninstall` from the **old** exe (or via `services.msc`). If the UI ever needs network/HTTPS access, configure a real cert under `Kestrel:Endpoints` and add `CookieSecurePolicy.Always` + `UseHttpsRedirection()`.

Tests live in the sibling **`BackupService.UnitTests`** project (in the solution). Stack: **NUnit** + **Moq** + **FluentAssertions**. Note FluentAssertions is pinned to **7.x** (the last Apache-2.0/free line — 8.x requires a paid commercial license); don't bump to 8.x without a license.

```powershell
dotnet test                                                   # run all tests
dotnet test --filter "FullyQualifiedName~TestClassName.TestMethodName"   # single test
```

Testing services that use the DbContext factory: mock `IDatabaseContextFactory` with Moq and have `CreateDbContext()` return a `BackupDbContext` over a **shared in-memory SQLite** connection (`new SqliteConnection("DataSource=:memory:")` kept open for the test, `EnsureCreated()` for schema) — see `Authentication/AdminCredentialServiceTests.cs` for the pattern. Use `NullLogger<T>.Instance` for `ILogger` dependencies.

### Database / EF Core migrations

Migrations are kept under `BackupService/Database/Migrations`. Always pass `--output-dir Database/Migrations` when adding one so it lands there rather than the default `Migrations/` folder. The `dotnet-ef` tool version must match the EF Core packages (currently 10.0.9).

```powershell
dotnet ef migrations add <Name> --project BackupService --output-dir Database/Migrations
dotnet ef database update --project BackupService     # apply migrations manually
dotnet ef migrations remove --project BackupService   # undo the last (unapplied) migration
```

The app also calls `db.Database.Migrate()` on startup, so pending migrations apply automatically when it runs. The SQLite file (`backupservice.db`, plus `-wal`/`-shm`) is generated in the **data directory** (`BackupDatabaseLocation` — per-user `%LOCALAPPDATA%\BackupService` for a deployed run, the `bin\…` output in Development) and is not source.

## Architecture

- `Program.cs` — host bootstrap via `WebApplication.CreateBuilder`. First dispatches the run mode (`-stop`/`-background`/foreground+`--worker`; see "Run modes" above) and acquires the single-instance lock, then builds the host with an explicit `ContentRootPath = AppContext.BaseDirectory`, registers the DB factory, cookie auth + authorization, Razor Components with interactive server rendering (`AddRazorComponents().AddInteractiveServerComponents()`), registers the backup scheduler as the hosted service, then maps the Blazor endpoint (`MapRazorComponents<App>().AddInteractiveServerRenderMode()`) and a `/logout` POST endpoint. The middleware pipeline is `UseAuthentication` → `UseAuthorization` → `UseAntiforgery` → `MapStaticAssets` → endpoints. Startup **first applies any staged database restore** (`DatabaseBackup.PendingRestoreApplier.ApplyIfPending`, deliberately before anything opens the DB — see `DatabaseBackup/`), then runs `db.Database.Migrate()` and `IAdminCredentialService.EnsureSeededAsync()`. **Static assets use .NET fingerprinting:** `app.MapStaticAssets()` (not `UseStaticFiles`) serves `wwwroot`, and `App.razor` links the stylesheet via `@Assets["app.css"]` so the URL carries a content hash — CSS/JS edits bust the browser cache automatically (avoids the stale-CSS problem where new markup loads but old styles persist).
- **Backup execution is driven by the scheduler, not a `Worker`.** (`Worker.cs` — the old idle heartbeat placeholder — has been removed; `BackupSchedulerService` is the `BackgroundService` now.) Backup logic belongs in the per-type handlers in `Scheduling/` (see below), not inline in the host.
- `Database/` — **all** database code lives here: `BackupDbContext` (EF Core, SQLite), the entity models, the `Migrations/` subfolder, `BackupDatabaseLocation`, and the `DatabaseContextFactory`. Keep new entities and DbContext changes in this folder. Core domain: a `Profile` has one-to-many `OneWaySyncItem` records (cascade delete); the `OneWaySyncItem` carries status enums (`OneWaySyncStatus`, `OneWaySyncLastRunStatus`). The second profile type, **`ProfileType.InstantSync`**, has its own one-to-many child, **`InstantSyncItem`** (cascade delete) — each with `Name`, `SourceFolder`, `TargetFolder`, an `int DebounceMilliseconds`, `IncludeSubFolders` and `AllowDeletions` (no status/overwrite columns — instant sync is source-authoritative and has no discrete run). The third profile type, **`ProfileType.ArchiveSync`**, has its own one-to-many child, **`ArchiveSyncItem`** (cascade delete) — each with `Name`, `SourceFolder`, `TargetFolder`, a `FileName` (the base archive name a timestamp is appended to), `IncludeSubFolders`, a `bool OnlyCopyOnChange` (when true, only create a new archive when the source content changed since the most recent one — see the fingerprint mechanism in `ArchiveSyncProcessor`), an `ArchiveCompressionLevel CompressionLevel` (Optimal/Fastest/SmallestSize/NoCompression — a project enum mapped to the BCL `CompressionLevel` via `ArchiveCompressionLevelExtensions.ToCompressionLevel()`; defaults Optimal), a `bool PasswordProtect` + a `string? PasswordEncrypted` (the archive password, **encrypted at rest** via `ISecretProtector` — same scheme as SMB; never stored/logged in plaintext) + an `ArchiveEncryptionMethod EncryptionMethod` (`Aes256`/`ZipCrypto`), an `ArchiveRetentionMode RetentionMode` (`KeepLastN`/`GrandfatherFatherSon`), an `int RetentionCount` (N — total for keep-last-N, per-level for GFS), an `int MaxLevels` (GFS level count; 1 otherwise) and an `int RunCount` (monotonic count of archives created — the only mutable run-state, drives the GFS promotion cadence; no Status/LastRunStatus columns). ArchiveSync is **scheduled** (uses `Profile.Schedule`/the scheduler, like OneWaySync — not watcher-driven). The fourth profile type, **`ProfileType.LightroomArchive`**, has its own one-to-many child, **`LightroomArchiveItem`** (cascade delete) — like `InstantSyncItem` (`Name`, `SourceFolder`, `TargetFolder`, `DebounceMilliseconds`, `IncludeSubFolders`, `AllowDeletions`) but with **only a connectable target** (the target connection is the profile-level `Profile.TargetConnectionId`; the source is local-only, since it's watcher-driven). It is **watcher-driven** like InstantSync, plus a per-copy raw-sidecar step: whenever a file is copied, its matching raw originals are pulled from a Lightroom catalog into a RAW folder beside the copy. Its three settings are **profile-level** (shared by all items) and live on `Profile` itself (the one type whose config isn't entirely on the child): `string? LightroomFolder` (the local catalog scanned recursively), `string? RawFormats` (CSV of extensions, e.g. `.DNG,.ARW`) and `string? RawFolderName` (the RAW sub-folder name, default `RAW`) — see `LightroomArchiveSettings` + `LightroomArchiveProcessor` in `Scheduling/`. The fifth profile type, **`ProfileType.TwoWaySync`**, has its own one-to-many child, **`TwoWaySyncItem`** (cascade delete) — like `OneWaySyncItem` (`Name`, `SourceFolder`, `TargetFolder`, `IncludeSubFolders`, both sides connectable) but reconciled **bidirectionally**: in place of `OverwriteBehaviour`/`AllowDeletions` it carries a `ConflictResolution ConflictResolution` (NewerWins/SourceWins/TargetWins/KeepBoth/Skip; default NewerWins — how a file changed on *both* sides since the last sync is resolved) and a `bool PropagateDeletions` (default true; when false a one-sided deletion is restored from the surviving side rather than mirrored to it). It is **scheduled** (like OneWaySync/ArchiveSync) and has **no run-state columns** (no Status/LastRunStatus); its per-item **baseline** — the last-synced state that lets the engine tell a deletion from a new file — is a **file-based manifest** at `{data dir}\two-way-sync\{itemId}.manifest` (see `TwoWaySyncStateStore`/`TwoWaySyncEngine` in `Scheduling/TwoWaySync/`), never the database. A profile uses the child collection matching its `Type` (`OneWaySyncItems`, `InstantSyncItems`, `ArchiveSyncItems`, `LightroomArchiveItems` or `TwoWaySyncItems`); the others stay empty. **`OneWaySyncItem`, `ArchiveSyncItem` and `TwoWaySyncItem` each own a one-to-many `Filters` collection** (`OneWaySyncFilter` / `ArchiveSyncFilter` / `TwoWaySyncFilter`, cascade-deleted via the default required-FK convention) — include/exclude rules each with a `FilterDirection Direction` (Include/Exclude), a `FilterKind Kind` (File/Folder/**Path**) and a `Pattern`. File/Folder are **name-only wildcards** (matched in every sub-folder); **`Path` (exclude only)** is a literal path *relative to the source root*, matched against the exact location (that file, or that folder and its whole subtree) — not by name. Empty includes = back up everything; see `BackupFilter` in `FileSystem/`. **A profile's own run status (`ProfileStatus` — Idle/Running/Error) is deliberately NOT persisted** — it describes the current run and is tracked in memory by `IProfileStatusService` (see `Profiles/`); there is no `Profile.Status` column. Each `OneWaySyncItem` also has an `OverwriteBehaviour` enum (how to treat an existing/newer file at the destination). `Profile` has a `bool Enabled` (on/off switch) that **defaults to true** via a store default — `BackupDbContext.OnModelCreating` configures `Property(p => p.Enabled).HasDefaultValue(true)` so the migration backfills existing rows to enabled; the C# initializer is also `= true`. (EF Core 7+ then treats `true` as the sentinel, so a `false` value is still persisted — disabling a profile works.) `Profile` also carries **per-profile notification settings** — `bool NotificationsEnabled` (master switch, store default true), `bool NotifyOnStart` (default false), `bool NotifyOnComplete` (store default true) and `bool NotifyOnEject` (default false; OneWaySync/ArchiveSync/TwoWaySync only — fires when the profile ejects a USB drive) — edited on the **Notifications** tab of `ProfileDialog` and read by the backup handlers / USB watcher (see `Notifications/`); `NotificationsEnabled`/`NotifyOnComplete` use the same `HasDefaultValue(true)` backfill as `Enabled`. A separate `bool ShowProgressWindow` (default false) on the same tab opts the profile into an on-screen progress window while it runs (Windows-only; rendered by `Notifications/WindowsProgressWindowService`). A `bool EjectAfterRun` (default false) safely removes the profile's mass-storage USB device(s) after a device-triggered run (see `Scheduling/Usb/`). `Profile` also has a nullable `DateTimeOffset? DateNextRun` (the next scheduled run time, written by the scheduler — see `Scheduling/`) and a `bool HandleMissedSync` (when true, a scheduled profile that missed its run while the service was down runs immediately on the next startup; only meaningful for scheduled types). Other tables: `AdminCredential`, `AuthenticationHistory`, `BackupRecord` (a placeholder, **never written**), **`BackupRun`** (structured run history for the dashboard — one row per discrete scheduled/manual run, covering **both** backup runs and **scheduled-task** runs, distinguished by a `RunKind Kind` (Backup/ScheduledTask): a **nullable** `int? ProfileId` FK (cascade-delete; set for a backup run) **and** a nullable `int? ScheduledTaskId` FK (cascade-delete; set for a scheduled-task run), denormalised `ProfileType Type` (unused for scheduled-task runs), `StartedUtc`, `long DurationMs`, `RunOutcome Outcome` (Success/**CompletedWithWarnings**/CompletedWithErrors/Failed), `Copied`/`Updated`/`Deleted`/`Errors`/**`Warnings`**/**`long BytesCopied`** (total bytes written; all zero for a scheduled-task run), `bool Manual`, and a loose `int? OperationLogId` for drill-through; written by `IBackupRunRecorder` — `RecordAsync` from each backup handler, `RecordScheduledTaskAsync` from the scheduled-task runner — see `Scheduling/`/`Dashboard/`), **`ScheduledTask`** + its one-to-many **`ScheduledTaskStep`** (cascade delete — the Scheduled Tasks feature; a cron-scheduled task that runs one or more ordered OS-command steps. `ScheduledTask`: `Name`, `Description?`, `bool Enabled` (default true), `string? Schedule` (cron), `DateTimeOffset? DateNextRun`, `bool HandleMissedSync`, `DateLastRun`, `DateCreated` — mirrors `Profile`'s scheduled fields but is **not** a profile. `ScheduledTaskStep`: `int Order` (ascending = run order), `string? Name`, a `ScheduledTaskStepKind Kind` (**Command** or **PowerShell**), and the per-kind fields — Command kind uses `string? Command` (executable path, or full command line when `RunViaShell`), `string? Arguments` (ignored when `RunViaShell`) and `bool RunViaShell`; PowerShell kind uses `string? Script` (the inline script body) — plus a shared `string? WorkingDirectory`. See the `ScheduledTasks/` + `Scheduling/ScheduledTasks/` folders), and `LogRetentionSettings` (a **single-row** settings table — `AuthenticationLogRetentionDays` default 7, `OperationLogRetentionDays` default 30 — seeded lazily by `ILogRetentionService`; drives the log-purge below), and **`DatabaseBackupSettings`** (another single-row, lazily-seeded settings table — the Database Backup feature's `Enabled` (default false), `TargetConnectionId` (nullable FK to `Connection`, **`SET NULL`** on delete), `TargetFolder`, `Schedule` (cron) and `MaxBackups` (default 5); owned by `IDatabaseBackupService` — see `DatabaseBackup/`). There is also the operation-logging header table `OperationLog` (unbounded `Name`, `TimestampUtc`, an `OperationLogLevel` enum — Info/Warning/Error/Debug — the **severity of the operation as a whole**, and a nullable `string? LogFile`). **Detail lines are no longer database rows** (there were far too many and each was a write-heavy insert): they live in a **per-log text file** (named `{id}.log` under `{data dir}\operation-logs`, referenced by `LogFile`), written/read via `IOperationLogFileStore` (see `Logging/`). `LogFile` is null for a detail-less/self-describing log (the whole message is in `Name`) and is set on the header the first time a line is written — its presence is what makes the Logs grid show an expand control. **The header `Level` is derived from the lines, not set independently:** it is the most severe of its lines' levels — all Info/Debug → Info, any Warning → Warning, any Error → Error (Debug counts as Info) — maintained by `OperationLogger` as lines are appended (a header only ever rises; the header row is touched only on the first write, on a level escalation, and on the summary rewrite — not per line). A **one-time** `OperationLogFileMigrator` (run at startup after `Database.Migrate()`) copies any legacy `OperationLogDetails` rows into files and drops that table. `OperationLog` also has a **nullable** `int? ProfileId` FK to `Profile` (null for logs not tied to a profile) configured in `OnModelCreating` with `OnDelete(DeleteBehavior.Cascade)` — deleting a profile cascade-deletes its logs (cascade is the non-default behaviour for a nullable FK, so it's set explicitly). Note the profile *deletion* log is deliberately left unassociated (`ProfileId` null) so it survives the delete. Written via the `Logging/` factory; read/displayed by the Logs sidebar section.
  - **Factory pattern — the `DbContext` is NOT registered in DI.** Instead `IDatabaseContextFactory` (impl `DatabaseContextFactory`) is registered as a singleton. Code that needs the database injects `IDatabaseContextFactory` and calls `CreateDbContext()`, owning and disposing a short-lived context per unit of work (`using var db = factory.CreateDbContext();`). Do **not** add `AddDbContext<BackupDbContext>` back. `DatabaseContextFactory` also implements `IDesignTimeDbContextFactory<BackupDbContext>` so `dotnet ef` can build a context at design time without the context being in DI.
  - **SQLite caveat:** SQLite cannot `ORDER BY` (or compare) a `DateTimeOffset` column. For "newest first" ordering use the autoincrement `Id` (monotonic with insertion) rather than a timestamp column — see `AuthenticationHistoryService.GetPageAsync`. `DateTimeOffset` columns are fine to store and `SELECT`/display.
  - **Database location is per-user** (`BackupDatabaseLocation.GetConnectionString()`): one SQLite file per user. A deployed run (any non-`Development` environment) puts it (and the data-protection key ring, the `logs\` folder and the PID file) under **`%LOCALAPPDATA%\BackupService`** — `Environment.SpecialFolder.LocalApplicationData`, *not* Roaming, since a SQLite file must not roam — so multiple Windows users each get an isolated config; a `Development` run keeps it next to the build output (`AppContext.BaseDirectory`, the `bin\…` folder) for the dev workflow. The decision reads `ASPNETCORE_ENVIRONMENT` directly (it runs before the host is built). There is no connection string in `appsettings.json` — it is computed in code. The key ring is **not** migrated — the old service's LocalSystem-DPAPI key ring isn't decryptable by a normal user — so SMB/Google-Drive passwords carried in the moved DB are unreadable and must be **re-entered** (already the supported `ConnectionSecretMigrator` "logged for re-entry" path).
- `Components/` — the Blazor Server UI. `App.razor` is the root HTML document (loads `_framework/blazor.web.js` and the theme `app.css`), `Routes.razor` wires the router via `AuthorizeRouteView` (unauthenticated → `RedirectToLogin`), and routable pages live in `Components/Pages/` (`@page` directives). `_Imports.razor` holds shared `@using`s for the component tree. Two layouts: `Components/Layout/MainLayout.razor` (default — top bar with signed-in user + Log out, gated by `<AuthorizeView>`, content in `.page`) and `Components/Layout/AuthLayout.razor` (full-screen centered, used by `Login` via `@layout AuthLayout`).
- **Layout shell:** `MainLayout` wraps the top bar + `<main class="app-main">` in `.app-shell` (a flex column at `height: 100vh`), so `.app-main` fills the viewport below the title bar. Pages that want a centred, max-width look opt into a `.page` wrapper; pages that need full height/bleed use `.app-main` directly.
- **Workspace pages (sidebar + content):** both the home **`BackupServicePage`** (route `/`, title "Backup Service") and the **Settings** page use the shared `.workspace` / `.sidebar` / `.sidebar-item` / `.workspace-content` CSS: a left-docked navigation sidebar (a self-contained control owning its items, two-way `@bind-SelectedKey`) plus a content area that swaps the selected section's control. `BackupServicePage` has `BackupServiceSidebar` (items: Dashboard → `Dashboard.razor`, Backup Profiles → `Profiles.razor`, **Groups → `GroupsControl.razor`**, **Scheduled Tasks → `ScheduledTasksControl.razor`**, Connections → `ConnectionsControl.razor`, Logs → `Logs.razor`); the **Dashboard** section renders run statistics + **ApexCharts** (see the `Dashboard/` bullet); the **Scheduled Tasks** section is a Profiles-style grid of cron-scheduled command tasks (see the `ScheduledTasks/` bullet); Settings has `SettingsSidepanel` (items: Authentication → `AuthenticationPanel`, Logging → `LoggingPanel` (log retention settings, `Components/Pages/Logging/`), **Database Backup → `DatabaseBackupPanel`** (application-database backup/restore, `Components/Pages/DatabaseBackup/` — see the `DatabaseBackup/` bullet), **Options → `OptionsPanel`** (desktop-integration toggles, `Components/Pages/Options/`)). Add a section = one sidebar `NavItem` (key/label/icon) + a matching `case` arm + a panel control. The **Logs** section is a **static** table of `OperationLog` headers (newest first, via `IOperationLogService`; **no paging** — every matching row loads into one scroll panel (`PageSize` unbounded), and **no live push** — it does *not* subscribe to `ILogWatcher`; it also **hides the in-progress run's log** (`ExcludeInProgressRuns` drops the newest log of any profile currently `Running`, read from `IProfileStatusService` once at load) so only **finished** runs are listed — a live run is followed in the **View Progress dialog** instead) — each row shows the header's level as a coloured `.log-level` pill, the associated **Profile** name (or a muted `—` when not tied to one), the log name, and timestamp, plus a `+`/`−` button that expands a **terminal-style view** of that log's lines — loaded as a bounded **window**, never the whole file: expand fetches the newest 1,000 logical lines (`DetailWindowLines`, via `IOperationLogService.GetDetailWindowAsync` → `IOperationLogFileStore.ReadWindowAsync` — one streaming pass returning an `OperationLogWindow`: the lines plus the file's **total line count** and **whole-file Warning/Error counts**), and a `.log-detail-meta` row shows "Showing the last N of M lines" with a **Load previous 1,000** button that walks backwards chunk-by-chunk (`LoadEarlierAsync` prepends the earlier window), so a 200k-line log is browsed in bounded slices — monospace `[{level}] [{timestamp}] {message}` rows (long lines **wrap** to the panel width via `white-space: pre-wrap` + `overflow-wrap: anywhere`, so nothing overflows sideways), each line tinted by its own `Level` (Warning → amber, Error → red, Info/Debug → default), lazy-loaded on first expand and released on collapse (`ReleaseDetailState`; a (re)load collapses everything and clears all cached lines, and `Dispose` clears the lot). A `message` may itself contain **CRLFs** (a consolidated single row whose lines are split by `\r\n` — e.g. the ArchiveSync "Archived {n} file(s):" list); `.log-terminal-line` is `white-space: pre-wrap` so embedded newlines are preserved *and* long lines wrap. Above the terminal view sits a per-log `.log-detail-filter` bar — a free-text search box plus two level checkboxes, **Warning ({n})** and **Error ({n})** (labelled with the **whole-file** counts from the window read), plus a right-aligned **Download** link (the free-text input is wrapped in `.filter-clearable`, which shows a clear `&times;` button when it has content — the same wrapper/`.filter-clear` pattern used by the header name filter). **When any filter is active the terminal switches from the loaded window to a server-side, whole-file search** (grep semantics — with thousands of lines users search, they don't scroll): `IOperationLogService.SearchDetailsAsync` → `IOperationLogFileStore.SearchAsync` streams the file matching a case-insensitive `Message` `Contains` AND the ticked level set (both unchecked = all levels; ticking either shows **only** those levels — an additive OR), returning at most 500 lines (`MaxSearchMatches`) in file order plus the **total** match count (`OperationLogSearch`; the meta row shows "N matches in M lines — showing the first 500" when truncated). Typing is **debounced** (300 ms via a per-log `CancellationTokenSource` — every search is a file scan); a checkbox toggle searches immediately; clearing every filter returns to the window view. Each expanded log keeps its own state, keyed by log id (`_detailFilters`/`_detailWarning`/`_detailError`/`_searchResults`). The **Download** link fetches the raw log file via `GET /logs/{id}/download` — a minimal endpoint in `Program.cs` (`RequireAuthorization`, serves `{data dir}\operation-logs\{id}.log` as an attachment; the `download` attribute keeps Blazor's router from intercepting the click) — the escape hatch for logs no web view handles well. The lines render in a `.log-terminal` box capped at `max-height: 400px` that scrolls vertically beyond that (long lines wrap rather than scroll sideways — wrapping means variable row heights, which is why the terminal is a plain `@foreach` and **not** `<Virtualize>`, whose fixed `ItemSize` can't accommodate wrapped rows). The detail cache is a `List<OperationLogLine>`. The expand control only shows when the log actually has lines — the grid hides the `+` when `OperationLog.LogFile` is null (no file was ever written), so self-describing logs (message-in-name, no sub-entries) render as a plain row. Above the table a `.filter-bar` has a free-text name filter (live, `@oninput`), an **Include Messages** checkbox, a level `Dropdown` (`OperationLogLevel?`, null = "All levels"), and a profile `Dropdown` (`int?` profile id, null = "All profiles"; options come from `IProfileService.GetSummariesAsync`). `GetPageAsync(page, size, filter, includeMessages, level, profileId)` does the matching — name via `EF.Functions.Like` (LIKE is case-insensitive for ASCII in SQLite), an exact `Level` match, and an exact `ProfileId` match (all server-side, AND-combined, each returned log's `Profile` navigation `Include`d). **Include Messages** can't be done in SQL any more (lines are in files), so that one branch pulls the level/profile-filtered headers into memory and keeps a log when its name matches **or** its file contains the text (`IOperationLogFileStore.ContainsAsync`), then pages in memory.
- **Naming caveat:** never name a type or page folder `BackupService` — it equals the root namespace and shadows it (breaks `@using BackupService...`). The home page folder/class is `BackupServicePage` for this reason.
- **Interactivity:** pages are static SSR by default. Components needing interactivity opt in with `@rendermode InteractiveServer` (infrastructure already wired in `Program.cs`). The Settings page is the first such page (the `SettingsSidepanel` nav updates the shown section via `@bind-SelectedKey`).   - **The scheduler that actually fires profiles** also lives here. `BackupSchedulerService` is a singleton registered in **three roles** — itself, `IBackupScheduler`, and the hosted `BackgroundService` (one shared instance via `AddSingleton(...)` + `AddSingleton<IBackupScheduler>(sp => sp.GetRequiredService<...>())` + `AddHostedService(sp => ...)`). On startup it loads every enabled profile that has a `Schedule` and registers it; a loop computes each profile's next run with Cronos (`CronExpression.GetNextOccurrence(DateTimeOffset.Now, TimeZoneInfo.Local)` — **local wall-clock, DST-correct**), waits until the soonest (capped at 1 min, and woken early on change via a `SemaphoreSlim`), then fires every due profile. **Jobs run concurrently** (each due profile launched on its own `Task.Run`, so a slow backup never blocks others) and a profile is **never run twice at once** — before spawning a thread the scheduler skips a profile whose run is still in progress (`IProfileStatusService.IsRunning`), and `BackupRunner` re-checks atomically via `TryBeginRun` (the authority). It reads profiles via `IDatabaseContextFactory` directly (not `IProfileService`) to avoid a DI cycle. The `IBackupScheduler` API is a single `SyncAsync(profileId)` that re-reads the profile and schedules it (enabled + parseable cron) or unschedules it (missing/disabled/blank/invalid) — `ProfileService` calls it after **every** mutation (`CreateAsync`/`UpdateAsync`/`SetEnabledAsync`/`DeleteAsync`) so edits take effect immediately. (`GetNextOccurrence(cron, from, tz)` is a pure static helper, extracted for tests.) **The scheduler is the single writer of `Profile.DateNextRun`** — it persists the computed next-run time (via `ExecuteUpdateAsync`, no load) whenever a schedule is registered (`SyncAsync`/startup), advanced after firing, or cleared on unschedule (null) — so the upcoming run is recorded for every scheduled profile and survives a restart. **Missed-run catch-up:** on startup `LoadAllAsync` reads each enabled scheduled profile's `HandleMissedSync` + its *previously persisted* `DateNextRun`; if `ShouldCatchUp(handleMissedSync, persistedNextRun, now)` (a pure static helper — true only when opted in **and** the recorded next-run is in the past, i.e. the service was down for it) it writes a **visible profile-associated operation log** ("Missed scheduled run for '{name}' (was due …) — running now on startup", via the injected `IOperationLogFactory`) so the catch-up is distinguishable in the Logs section, then fires the profile via the normal `FireJob` path (`manual: false`). Only one catch-up runs per startup however many occurrences were missed.
  - **What runs when a schedule fires is dispatched by `ProfileType`.** `IBackupRunner`/`BackupRunner` (singleton) is the dispatcher: `RunAsync(profileId, manual = false)` loads the profile **with its `OneWaySyncItems`**, **skips the run if the profile is locked** (`IProfileStatusService.IsLocked` — an admin has it open in an edit/delete dialog), otherwise sets the in-memory status to `Running`, **acquires the profile's group gate** (`Scheduling/Groups/IGroupRunGate`/`GroupRunGate` — a capacity-1 `SemaphoreSlim` per **Sequential** group id, released via `IAsyncDisposable`; members of a Sequential group queue and run one at a time, while a Parallel-group or ungrouped profile acquires nothing — see `Groups/`), then **serialises USB access** (`Scheduling/Usb/IUsbRunGate`/`UsbRunGate` — a per-connection-id `SemaphoreSlim`; the run waits here until any other run using the same USB device finishes, so profiles sharing a slow USB drive or MTP device queue and run one at a time; `TryBeginRun` marks the profile `Running` *before* these waits so it can't be double-spawned while queued), runs the handler, **stamps `DateLastRun` (the only DB write — status is no longer persisted) and *then* flips the status to `Idle`** (order matters: the grid reloads on the status change, so the timestamp must be saved first or the grid shows the previous run's `DateLastRun`). On failure the handler has already set `Error`; the runner stamps `DateLastRun` and re-asserts `Error` so the grid's status-triggered reload also picks up the fresh timestamp. It does **not** write its own operation log — **the handler owns the single per-run log** (see next). It calls the `IProfileTypeHandler` whose `Type` matches `profile.Type` (handlers injected as `IEnumerable<IProfileTypeHandler>`, indexed into a dictionary); an unmapped type is the one case the runner itself logs (a "Scheduled backup failed" error log) since no handler runs. On a handler exception the runner just records the failure via `ILogger` (the handler already set `Error` status and logged — see next). **A run is either scheduled or `manual`** — `manual: true` is a "Run now" from the Profiles grid (see `Profiles/`), routed through the *same* `RunAsync` so it goes through the identical status/locking/single-instance path; the only difference is the run's operation log is **prefixed `[Manual] `**. **`IBackupRunner.RequestStop(profileId)`** (the grid's Stop button) cancels an in-progress run: the runner wraps each run in a linked `CancellationTokenSource` registered per profile id (also linked to the host's `ApplicationStopping`, an optional `IHostApplicationLifetime` ctor dependency, so app shutdown stops a run even when no caller token was passed), and `RequestStop` cancels it; the handler catches the `OperationCanceledException`, finishes its log as a **Warning** ("cancelled"), and the runner's `catch … when (cts.IsCancellationRequested)` returns the profile to **Idle** (not Error) to await its next scheduled run — the crash-safe copy deletes any partial temp on cancel, so nothing is left behind. `IProfileTypeHandler` is the per-type seam (`ProfileType Type { get; }` + `HandleAsync(Profile, manual, ct)`); `OneWaySyncHandler` (`Type => ProfileType.OneWaySync`) and `InstantSyncHandler` (`Type => ProfileType.InstantSync` — a manual full reconcile, see the InstantSync bullet below) are the two so far. (`BackupRunner` `Include`s both `OneWaySyncItems` and `InstantSyncItems` so whichever handler runs has its items.) It creates **exactly one** `OperationLog` per run: the header starts as `"{prefix}{Type.GetDescription()} Handler called with {n} one way sync item(s)."` (e.g. "One Way Sync Handler called with 2 one way sync item(s).", or "[Manual] One Way Sync Handler …" for a manual run), and a `finally` rewrites the header (via `SetSummaryAsync`) to `"{prefix}… ran successfully in {duration} — {c} copied, {u} updated, {d} deleted"` (Info) or `"{prefix}… completed with {n} error(s) in {duration} — …"` (Error when any file/folder op errored) or `"{prefix}… completed with {n} warning(s) in {duration} — …"` (**Warning** — errors==0 but files were skipped as a non-fatal warning, e.g. locked) or `"{prefix}… failed in {duration}"` (Error for a *catastrophic* failure outside the per-pair loop). Precedence: any error ⇒ "errors"; else any warning ⇒ "warnings"; else success. The "{ProfileType description} Handler" prefix is derived from the enum's `[Description]`, and the log already carries the profile via its FK. **Each handler also records one structured `BackupRun` row per run** via `IBackupRunRecorder`/`BackupRunRecorder` (singleton, DB factory; `Scheduling/`): in the same `finally`, before the `SetSummaryAsync` rewrite (so the row exists before the summary's `ILogWatcher.Notify` reaches the dashboard), it derives a `RunOutcome` (fatal → Failed; else errors>0 → CompletedWithErrors; else warnings>0 → CompletedWithWarnings; else Success) and inserts a row with the duration, the `BackupResult` counts (incl. `Warnings`), `manual`, and `log.OperationLogId`. This is the **only** structured run history (the `OperationLog` summary is free text); the dashboard reads it via `Dashboard/IDashboardService`. The continuous InstantSync/LightroomArchive watchers don't go through the handlers/runner, but **each flush that does real work records its own `BackupRun` row** (via the same `IBackupRunRecorder`, `manual: false`, guarded by `DeferredOperationLogger.WasCreated` so a no-op flush records nothing) — so live watcher activity shows in the dashboard's Recent Runs alongside scheduled/manual runs. **The actual file work is `IOneWaySyncSynchronizer`/`OneWaySyncSynchronizer`** (singleton; see `FileSystem/`/`Scheduling/`): for each pair the handler sets `OneWaySyncItem.Status = Running` (DB), appends a `"One way sync '{Name}': {src} -> {tgt}"` line, calls `synchronizer.SyncAsync(pair, log, ct)`, aggregates the returned `BackupResult` (Copied/Updated/Deleted/Errors/**Warnings**/**BytesCopied** — a file that **couldn't be read** (locked by another process, *or* an unavailable cloud file such as a OneDrive files-on-demand placeholder a session-0 service can't hydrate) is a non-fatal Warning, not an Error; see `FileSystem/FileLock` — `IsSkippableReadError(ex, out reason)` classifies lock/sharing violations *and* the `ERROR_CLOUD_FILE_*` family (Win32 358–405) and yields the warning reason; each engine's crash-safe copy adds the written file's size to `BytesCopied` via `IBackupFileSystem.GetFileSize`), then persists `LastRunStatus = Success/Fail` + `Status = Idle`. A per-pair unexpected exception is logged and the run continues with the other pairs; only a catastrophic failure sets the in-memory `ProfileStatus.Error` and re-throws (per-file errors stay logged-but-non-fatal — the Error detail lines escalate the header to Error and the pair's `LastRunStatus` is `Fail`, but the run completes and the grid status stays Idle). **Add a profile type = one `IProfileTypeHandler` impl + its `AddSingleton<IProfileTypeHandler, …>()` registration** — no scheduler/runner change; each handler owns its single per-run log.
  - **The folder-pair sync engine** — `IOneWaySyncSynchronizer`/`OneWaySyncSynchronizer` (singleton) — resolves the pair's **source and target each to an `IBackupFileSystem`** via `IEndpointFileSystemFactory` (local, or a remote SMB connection per `OneWaySyncItem.SourceConnectionId`/`TargetConnectionId`; sessions disposed in a `finally`), then walks the source tree **one folder at a time** and mirrors it into the target — a copy **streams from the source filesystem into a crash-safe temp on the target filesystem** (`OpenRead`→`OpenWrite`→stamp timestamp→rename), so local↔SMB copies work either direction, logging **only operations actually performed** (no line for an unchanged file) to the run's `IOperationLogger` and returning a `BackupResult`. Per file, by `LastWriteTimeUtc` with a **2-second tolerance** (`WriteTimeTolerance`, like robocopy `/FFT` — FAT/exFAT USB drives store 2-second-granularity times that round up, so an exact compare would see every unchanged file as "newer" and re-copy it every run): destination missing or source newer beyond the tolerance → copy; within tolerance → skip (unchanged) — **unless the destination is shorter than a source of known (positive) size**, the mark of an earlier copy that ended early yet was stamped with the source's time: that one is re-copied and logged as a **Warning** that counts toward `BackupResult.Warnings` ("Repaired …"), except that a destination reading as marginally *newer* within the tolerance is only replaced under `AlwaysOverwrite` (`IsTruncatedCopy`/`MayReplaceDestination`). A *larger* destination, or a source reporting no usable size (≤ 0 — an MTP device can report 0, or a sentinel that overflows to -1, for a real file), is never "repaired" (either would re-copy the same file every run). The compare reads each side's time **and** size in one `IBackupFileSystem.GetFileStat` lookup, so the check adds no round trips; destination newer beyond the tolerance → the pair's `OverwriteBehaviour` (`DoNotOverwriteNewer` skip / `AlwaysOverwrite` overwrite / `UpdateOnlyIfContentMatches` → if byte-equal, sync the destination's timestamp to the source's, else skip). `IncludeSubFolders` → depth-first recursion; `AllowDeletions` → **full mirror** (delete orphan target files *and* orphan sub-folders recursively — but inside an orphan folder the include/exclude rules still apply, so out-of-scope files and excluded sub-folders are kept along with the folder, and a **directory link** (junction/symlink, `IBackupFileSystem.IsDirectoryLink`) is removed as a link, never walked into). A file that vanishes between the folder listing and its stat/copy is skipped quietly (a vanished destination is just copied afresh), not reported as an error. **Copies are crash-safe:** every copy/overwrite is written to a dot-prefixed `.{name}.tmp` in the target folder via `CopyThroughTempAsync` (the deterministic name comes from `CrashSafeTempName`), then (on success) the original is deleted and the temp renamed onto it; on **any** error the temp is removed (best-effort) so a partial/temp file is never left behind. The copy counts the bytes it streams (`BytesCopied` is that count — the temp is never stat'ed) and **never commits a short copy** (fewer bytes than the source's known size): if the source's size has since changed (it was saved/truncated mid-copy) the file is skipped as a **Warning** and retried next run, otherwise it's an **Error** ("Incomplete copy"). The run's token reaches `OpenRead(path, ct)` so a Stop interrupts MTP/Drive downloads too. **A leftover temp from a previously interrupted run** (e.g. the machine hibernated mid-copy, so cleanup couldn't run) is swept at the start of each target folder's processing: a `.{name}.tmp` (recognised by `IsCrashSafeTempName`) that isn't itself a source file is deleted regardless of `AllowDeletions` and excluded from the rest of that folder's pass — a genuine source file matching the pattern is protected by the source-name check. A file write/delete failure or a folder-access failure is logged as an **Error** line with the reason and counts toward `Errors` (the run continues). All filesystem access goes through **`FileSystem/IBackupFileSystem`/`BackupFileSystem`** (singleton; a thin `System.IO` wrapper) so the engine's rules and cleanup-on-error are unit-tested against a fake (`OneWaySyncSynchronizerTests`).
  - **InstantSync (the second profile type) is watcher-driven, not scheduled.** It has its own background driver, **`InstantSyncWatcherService`** (singleton in **three roles** like `BackupSchedulerService` — itself, `IInstantSyncManager`, hosted `BackgroundService`). On startup it attaches a `FileSystemWatcher` to each item of every **enabled** `InstantSync` profile; **`IInstantSyncManager.SyncAsync(profileId)`** (the watcher counterpart of `IBackupScheduler.SyncAsync`) re-reads the profile and (re)attaches or tears down its watchers — **`ProfileService` calls both `scheduler.SyncAsync` and `instantSyncManager.SyncAsync` after every mutation** (each is a no-op for the wrong type), so enabling/disabling/editing/deleting an InstantSync profile starts/stops its watchers immediately. Per item, change events are **debounced** (`DebounceMilliseconds`): events accumulate in pending change/delete sets behind a gate lock, a timer is re-armed on every event, and when it fires after the quiet window the batch is processed on a **single in-flight pass** (a **folder** in the batch is one that *arrived* — the watcher drops a folder's own "changed" events and queues only created/renamed ones — and its whole subtree is copied, because Windows reports a folder rename or move-in as one event with nothing for the files inside; a non-recursive item ignores sub-folders entirely, neither copying nor deleting them) (a `_processing` flag + a re-arm in the `finally` guarantees no lost events and no overlapping pass — the "handle incoming changes while copying" requirement). **Nothing a watcher reports is dropped silently:** a flush that **fails outright** (the processor throws — e.g. the target is unreachable) puts its batch back and is **retried indefinitely with backoff** (`RetryBaseDelay`, default 1 min, doubling to a 30-min cap; new events during the backoff wait for it) — only the **first** failure of a run of them writes an Error log and a Failed `BackupRun` (later ones go to `ILogger` only, so a target offline for a day doesn't add ~48 failures to Logs and the dashboard's success rate), and the flush that finally succeeds notes "working again after N failed attempt(s)"; a flush that ran but left **errors or warnings** (files it couldn't copy) is followed by a **catch-up pass** — a full reconcile of the item through `IOneWaySyncSynchronizer` (`AlwaysOverwrite`) — up to 6 times; a watcher **buffer overflow** (`InternalBufferOverflowException`, events lost) triggers a catch-up; any other watcher error (source folder gone, network) keeps **restarting the watcher** and catches up once it's back; and an item whose **source folder doesn't exist yet** at load (a drive not mounted at logon) is retried every `WatchRetryInterval` (default 1 min) and caught up once it can be watched — without stopping the profile's other items. `RetryBaseDelay`/`WatchRetryInterval` are internal test seams. Each item has a **per-item gate** shared across watcher instances, so the replacement watcher created by an edit never runs a pass while the old one's (cancelled) pass is still unwinding; disposing a watcher (edit/disable/delete/shutdown) **cancels its running pass**. Covered by `InstantSyncWatcherServiceTests` (real folders + a real `FileSystemWatcher`, fake processor). Each flush owns **one** profile-associated `OperationLog` (`"Instant Sync '{item}' — {n} change(s)"` rewritten to a summary, exactly like the handler pattern) — but via a **`Logging/DeferredOperationLogger`** so a flush that does no real work writes **no log at all**. (The `{n}` change count is the number of distinct queued path-events, not files copied; a build touching `bin` produces many directory touch-events and short-lived temp files that are no-ops at flush time — directory events whose target already exists, or files that vanished before the debounce settled — so without deferral they'd show up as noisy "synced N change(s) — 0 copied" entries.) The actual copy/delete is **`IInstantSyncProcessor`/`InstantSyncProcessor`** (singleton over `IBackupFileSystem`, unit-tested via `InstantSyncProcessorTests`): each changed source path is rebased under the target and copied **crash-safe** (the same dot-`.tmp`→rename idiom as `OneWaySyncSynchronizer`; the helper is duplicated, not shared); deleted source paths are mirrored only when `AllowDeletions`. InstantSync is **source-authoritative** (a changed file always overwrites the target — no `OverwriteBehaviour`). The manual **"Run now"** path reuses the runner/handler seam: `InstantSyncHandler` does a one-off full reconcile by mapping each `InstantSyncItem` onto a transient `OneWaySyncItem` (`OverwriteBehaviour.AlwaysOverwrite`) and calling the existing `IOneWaySyncSynchronizer` — so the grid's Run-now works unchanged. **Add a watcher-driven profile type = its own manager/processor/handler in this shape**, registered alongside these.
  - **ArchiveSync (the third profile type) is scheduled** (like OneWaySync — it fires from `BackupSchedulerService`, no watcher). Its handler is **`ArchiveSyncHandler`** (`Scheduling/ArchiveSync/`, `Type => ProfileType.ArchiveSync`), same shape as `OneWaySyncHandler`: one per-run `OperationLog` (`"[Manual] "`-prefixed for Run-now) rewritten in a `finally` to a summary (`"… ran successfully in {d} — {n} archive(s) created, {m} pruned"` / `"… completed with {e} error(s) …"` / `"… failed in {d}"`), per-item try/catch so one item's failure doesn't abort the rest. The actual work is **`IArchiveSyncProcessor`/`ArchiveSyncProcessor`** (singleton over `IBackupFileSystem`, unit-tested via `ArchiveSyncProcessorTests`): per item it (1) builds a ZIP of the source in a **local temp folder** (`IBackupFileSystem.GetTempFilePath` + `CreateZipFromDirectory`, which returns the entry names it added — these are **verbose-logged at `OperationLogLevel.Debug`** as a **single** detail row, `"Archived {n} file(s):"` followed by one file per **CRLF-separated** line, rather than thousands of rows; the file list can't change mid-zip and Debug counts as Info for the header; each entry is compressed at the item's `CompressionLevel`, and when `PasswordProtect` the processor decrypts `PasswordEncrypted` via `ISecretProtector` and passes it to `CreateZipFromDirectory` to **encrypt** the archive (AES-256 or ZipCrypto per `EncryptionMethod`) — a protected item with no/undecryptable stored password errors rather than producing an unencrypted zip), (2) **crash-safe copies** it into the target as `{FileName}_{yyyy-MM-dd_HHmmss}.zip` (the same dot-`.tmp`→rename idiom, duplicated; an archive that **already exists under that name is never replaced** — the item errors instead), then (3) applies **retention** (not cancellable part-way, so a Stop can't leave it half-done). The local temp zip and its folder are always removed afterwards; a **Stop during the zip build** is checked per entry and is a cancellation, not an error. **"Only copy on change"** (`ArchiveSyncItem.OnlyCopyOnChange`): before zipping, `ComputeSourceFingerprint` builds a **manifest** of every archived file's SHA256 (one ordinal-sorted `{entry}\t{hash}` line per file, matching the archived set's recursion + include/exclude filtering) into a local temp file, then hashes that manifest → a single source fingerprint. (A file that can't be read here — e.g. a OneDrive cloud-only placeholder — is skipped from the manifest via `TryHashFile` rather than aborting the whole archive; the zip pass then flags it as a warning. See `FileSystem/FileLock`.) It looks at the **newest** existing target archive and reads its fingerprint from the ZIP's **archive comment** (`IBackupFileSystem.GetZipComment`); if it matches, the run is **skipped** (logged "Source unchanged … skipping", no zip, no copy, no retention, so `RunCount` doesn't advance). Otherwise the new fingerprint is stored in the created ZIP's comment (`CreateZipFromDirectory(…, comment)`). A null/unreadable comment always forces a rebuild — it never wrongly skips. The fingerprint runs against the **local** source (a remote source is already staged locally by this point). Timestamps are **local** wall-clock at second precision. **Retention modes** (`ArchiveRetentionMode`): `KeepLastN` deletes everything older than the newest N; **`GrandfatherFatherSon`** keeps N per level across `MaxLevels` levels — each archive's level is encoded in its name (`{FileName}_L{level}_{ts}.zip`) so retention is **derivable from the target folder listing** (a foreign/unparseable file is skipped, never deleted). The GFS algorithm, driven by the per-item **`RunCount`** (incremented only when an archive is actually created), on run index `k`: create the L1 "son"; for `L = 1..MaxLevels-1` (low→high) if `k % N^L == 0` **promote** (rename) the oldest at level `L` up to `L+1` (so a freshly-promoted father can cascade to grandfather the same run); then **trim** each level to N (deleting the aged-out, non-promoted archives; top-level overflow too). This gives true exponential spacing (L1≈last N runs, L2≈N², L3≈N³). The handler advances `RunCount` via a short-lived context after a successful create (mirrors `OneWaySyncHandler`'s per-pair status write). The manual **"Run now"** path is just `RunAsync(id, manual: true)` through the same runner/handler seam. **Add a scheduled profile type = its own handler (+ processor) in this shape**, registered alongside these.
  - **LightroomArchive (the fourth profile type) is watcher-driven** (like InstantSync, not scheduled), with an added raw-sidecar step. Its driver **`LightroomArchiveWatcherService`** (`Scheduling/LightroomArchive/`, singleton in three roles: itself, `ILightroomArchiveManager`, hosted `BackgroundService`) mirrors `InstantSyncWatcherService` — a debounced `FileSystemWatcher` per item, per-flush `DeferredOperationLogger` so no-op flushes write nothing, and the same retry/catch-up/missing-source/per-item-gate behaviour (a catch-up here feeds the processor **every** in-scope source file plus the pending changes, since it always flushes through its own processor; `LightroomArchiveWatcherServiceTests`) — and `ProfileService` calls `lightroomArchiveManager.SyncAsync(id)` after every mutation (alongside `scheduler`/`instantSyncManager`). The engine **`ILightroomArchiveProcessor`/`LightroomArchiveProcessor`** (singleton; unit-tested via `LightroomArchiveProcessorTests`) is **endpoint-aware** — modelled on `OneWaySyncSynchronizer`'s cross-filesystem copy, *not* the local-only `InstantSyncProcessor`: it injects `IEndpointFileSystemFactory` (resolve the target, local or a connection) + the local `IBackupFileSystem` (source + Lightroom catalog are always local), so the watcher has **no local/remote split** — it always calls `ProcessBatchAsync` regardless of target. Per changed source path it crash-safe-copies the file across the two filesystems (copy-if-missing-or-changed — unchanged means the same size and a `LastWriteTimeUtc` within the shared 2-second `WriteTimeTolerance` (via `GetFileStat`), so redundant events/reconciles don't re-transfer and a FAT/exFAT target's rounded times don't cause a re-copy every pass), **then** looks up the file's basename in a Lightroom raw **index** (basename → local raw paths, built **once per batch** from a recursive walk of `LightroomFolder`, matching the profile-level `RawFormats`, case-insensitive) and crash-safe-copies each match into a `{RawFolderName}` sub-folder **beside the copied file** (`{dir of rebased target}\{RawFolderName}\{raw}`). When several catalog raws share a file name (camera counters wrap), each is copied as `{stem} ({catalog folder}){ext}` (`DisambiguatedRawName`) so they can't overwrite each other. Deletions (only when `AllowDeletions`) mirror the rebased target *and* any matching raw(s) — plain or folder-tagged — in that sibling RAW folder, unless another source file with the same base name still sits beside the deleted one (its raws are shared). A folder that arrives (rename/move-in) is archived in full, as for InstantSync. The profile-level settings reach it via **`LightroomArchiveSettings`** (`FromProfile`: `LightroomFolder`, the parsed raw-extension set, `RawFolderName`; defaults `.DNG,.ARW`/`RAW`). The manual **"Run now"** path is **`LightroomArchiveHandler`** (`Type => ProfileType.LightroomArchive`, mirrors `InstantSyncHandler`: one `[Manual]`-prefixed per-run `OperationLog`, one `BackupRun` row): a **full reconcile** enumerating every in-scope source file per item (via the injected local `IBackupFileSystem`) and feeding them to `ProcessBatchAsync` as the changed set (no deletes). Like InstantSync, both the manual run **and each continuous watcher flush that does real work** record a `BackupRun` row (the watcher passes `manual: false`, guarded by `WasCreated`), so live activity appears in the dashboard's Recent Runs. **`LightroomArchiveItemService`/`ILightroomArchiveItemService`** (`Profiles/`, mirrors `InstantSyncItemService`) owns the item data; `ProfileService.CreateAsync`/`UpdateAsync` gained trailing optional params (`lightroomArchiveItems`, `lightroomFolder`, `rawFormats`, `rawFolderName`) and set the three profile-level fields.
  - **TwoWaySync (the fifth profile type) is scheduled** (like OneWaySync — fires from `BackupSchedulerService`, no watcher) but reconciles **both directions** with a persisted baseline. Its handler is **`TwoWaySyncHandler`** (`Scheduling/TwoWaySync/`, `Type => ProfileType.TwoWaySync`), same shape as `OneWaySyncHandler` (one per-run `OperationLog` rewritten to a summary in a `finally`, `[Manual] ` prefix for Run-now, per-item try/catch, `ProfileProgressReporter` progress, one `BackupRun` row, cancellation → Warning/Idle, start/complete notifications) — but it writes **no per-item status** (`TwoWaySyncItem` has no Status columns). The work is **`ITwoWaySyncEngine`/`TwoWaySyncEngine`** (singleton over `IEndpointFileSystemFactory` — both sides local or a connection, exactly like `OneWaySyncSynchronizer` — plus `ITwoWaySyncStateStore`; unit-tested via `TwoWaySyncEngineTests`). Per item it loads the item's **baseline manifest** (relative path → last-write-time + size, keyed by item id; file-based via **`ITwoWaySyncStateStore`/`TwoWaySyncStateStore`** rooted at `{data dir}\two-way-sync`, atomic temp-then-rename — the log-store precedent of keeping high-cardinality data out of the DB), walks the **union** of both trees one folder at a time (honouring `IncludeSubFolders` + the include/exclude `BackupFilter`), and for each file classifies each side vs the baseline as unchanged/added/modified/deleted (by `LastWriteTimeUtc` within the 2s `WriteTimeTolerance`, and size). **Reconcile:** only one side changed → apply it to the other (copy an add/modify; on a delete, delete the other side when `PropagateDeletions`, else restore from the surviving side); both changed → resolve per `ConflictResolution` (`NewerWins` newer→older, present beats delete; `SourceWins`/`TargetWins`; `KeepBoth` renames one to `{name} (conflict {ts}){ext}` so both end up on both sides; `Skip` leaves both + a Warning, keeping the old baseline so it re-flags). A fresh baseline is built as it goes and **saved only after a completed pass** (a cancelled/aborted run leaves the previous baseline, so nothing is mis-classified next run). **Safety rules that keep a baseline from turning into mass deletions:** (1) each manifest is **stamped with the folder pair it describes** (`EndpointKey` — both sides' connection id or `local` + folder, case-insensitive); loading it for a different pair (an item re-pointed to new folders or a new connection) returns an empty baseline — a "reset" run that copies both ways and deletes nothing, logged — while an unstamped manifest from before the stamp existed is trusted once and stamped on save; (2) once anything has been synced, **both root folders must exist** or the item is skipped with an Error (an unplugged drive, renamed folder or access-denied share would otherwise read as empty — "everything deleted" — and be propagated), while a first run simply creates a missing target; (3) a file whose fate wasn't settled this run — a failed state read, copy or delete, or a folder whose listing failed — **keeps its previous baseline entry** (`KeepBaseline`/`KeepBaselineUnder`), so next run judges it against the same state rather than mistaking a one-sided edit for a conflict or resurrecting a deletion; (4) a short copy is never committed (byte-counted, as OneWaySync); (5) the crash-safe temp is `.{name}.backupservice.tmp`, and only that suffix is ever swept — both sides are live user folders, so another app's `.x.tmp` is synced like any other file, never deleted. Copies are crash-safe (dot-`.tmp`→stamp-mtime→rename, duplicated) and stream across the two filesystems in either direction; unreadable/locked/cloud files are non-fatal Warnings via `FileLock.IsSkippableReadError`. Empty directories are not pruned (files-only deletions) and renames are delete+add (no rename detection). The data service is **`ITwoWaySyncItemService`/`TwoWaySyncItemService`** (`Profiles/`, mirrors `OneWaySyncItemService`; DTO `TwoWaySyncInput` with the two config fields + `Filters`); `ProfileService.CreateAsync`/`UpdateAsync` gained a trailing optional `twoWaySyncItems` param, and `DuplicateAsync` deep-copies the items + filters but **not** the baseline (a duplicate starts fresh). **Add a scheduled profile type = its own handler (+ engine/processor) in this shape**, registered alongside these.
- `FileSystem/` — `IFolderBrowser`/`FolderBrowser`: lists drives/subfolders on the server for the folder picker (admin-gated; inaccessible dirs skipped). Returns rich entries: `GetDrives()` → `DriveEntry(RootPath, Label)` (Explorer-style label e.g. `Windows (C:)`); `GetDirectories(path)` → `IReadOnlyList<FolderEntry>` (`FullPath`, `Name`, `DateModified`); `GetQuickAccess()` → the Desktop/Documents/Downloads/Pictures shortcuts that exist; `GetParent(path)`; and `CreateDirectory(parentPath, name)` → makes a sub-folder and returns its full path (used by the folder picker's New-folder button). Also `IBackupFileSystem`/`BackupFileSystem` (singleton) — a thin `System.IO`/`System.IO.Compression` wrapper (directory/file existence, list, copy, move, delete, timestamps, **`GetFileSize`** (for the bytes-copied stat), content-equal, plus `GetTempFilePath` for a unique local-temp path, `CreateZipFromDirectory` for archiving (its optional `comment` arg stores the ArchiveSync "only copy on change" fingerprint as the ZIP archive comment, `compressionLevel` sets how hard each entry is compressed, and a non-empty `password` encrypts the archive — AES-256 when `useAesEncryption` else legacy ZipCrypto. **The encrypted path uses SharpZipLib** (`ZipOutputStream`) since `System.IO.Compression` can't write encrypted zips; the unencrypted path stays on the BCL. `GetZipComment` reads the EOCD comment (still works on encrypted zips — the comment isn't encrypted)) and `GetZipComment` for reading that comment back (over SMB it tail-reads the EOCD record rather than downloading the whole archive)) used by the folder-pair sync engine (`Scheduling/OneWaySyncSynchronizer`), the instant-sync copy engine (`Scheduling/InstantSyncProcessor`) and the archive engine (`Scheduling/ArchiveSyncProcessor`) so their logic is testable against a fake; not unit-tested itself. **`IBackupFileSystem` also exposes `OpenRead`/`OpenWrite`** (stream primitives) so a copy can cross **two** filesystems (read from one, write to another), plus two default interface members a filesystem overrides when it can do better: **`GetFileStat`** (time + size in one lookup — `FileStat`; SMB uses one `FileNetworkOpenInformation` query, MTP one object lookup, Drive its cached entry) and a cancellable **`OpenRead(path, ct)`** (MTP/Drive, whose open is the whole download). `BackupFileSystem.GetFileSize`/`GetFileStat` report a **file symlink's target** length (`FileInfo.Length` is the link's own 0, but `OpenRead` follows the link). **`FileSystem/Smb/SmbBackupFileSystem`** implements the whole interface over a live SMBLibrary `ISMBFileStore` session (share-relative paths; streaming `SmbReadStream`/`SmbWriteStream` — a read checks the NT status **before** the data, since SMBLibrary leaves the data null on any failure and treating that as end-of-file silently truncated copies; `FileExists`/`DirectoryExists` open for attributes only and return false **only** for not-found statuses, throwing for anything else (access denied, a timeout) so a locked or unreachable entry is never read as deleted; the local-only `GetTempFilePath`/`CreateZipFromDirectory` throw `NotSupportedException`). **`FileSystem/IEndpointFileSystemFactory`/`EndpointFileSystemFactory`** resolves a folder-pair side — a `int?` connection id + configured path — to an `EndpointFileSystem(FileSystem, BasePath, Session)`: null id → the shared local `BackupFileSystem`; a set id → a connected `SmbBackupFileSystem` (via `IConnectionResolver`) rooted at the connection's `RootFolder`. The session is disposed after the run. *(SMB read/write is integration-only — not unit-tested; the engine's local↔remote logic is covered by a fake-filesystem cross-fs test.)* **In-use/locked files are handled, not fatal:** every source read uses a **permissive share mode** (`FileShare.ReadWrite | FileShare.Delete`) so a file another process holds open *for writing* (a log, a VS `.vsidx` index, …) can still be read — plain `File.Copy`/`CreateEntryFromFile` use only `FileShare.Read` and throw "being used by another process" on those. `CopyFile` is therefore a manual stream copy that then **re-stamps the destination's `LastWriteTimeUtc` from the source** (the sync engine compares write-times to decide copy/skip, so a naive copy's "now" timestamp would make every later run see the destination as newer); file *attributes* are intentionally not propagated. `CreateZipFromDirectory` builds the archive entry-by-entry and returns a **`ZipBuildResult`** (`Added` entry names for verbose logging + `Skipped` — `ZipSkippedFile(EntryName, Reason)` — for files that *still* couldn't be read): a single locked file is **skipped, not fatal**, so one bad file never aborts the whole archive. A file that opens but fails part-way through its read has already started its entry (which can't be removed from an archive being written), so the archive is **rebuilt without it** rather than keeping a truncated entry; a *write* failure (e.g. the temp disk filling) fails the archive. `ArchiveSyncProcessor` logs each skip as a **Warning** detail line and increments the run's **warning** count, so the handler's summary reports "completed with N warning(s)" while the archive is still produced from the readable files. (The ArchiveSync "only copy on change" fingerprint pass, `ComputeSourceFingerprint`/`TryHashFile`, likewise tolerates an unreadable file — it's omitted from the manifest rather than aborting the whole archive, leaving the zip pass to flag it as the warning, so a cloud-only file no longer fails the run.) A OneWaySync/InstantSync copy that still fails on an unreadable file is caught by the existing crash-safe `CopyThroughTempAsync`, which classifies it via **`FileLock.IsSkippableReadError(ex, out reason)`** — a **`FileNotDownloadableException`** (thrown by a filesystem for a file it can never download — a Google Docs/Sheets/Slides file or shortcut on Drive — carrying its own `Reason`), a Win32 sharing/lock violation (HRESULT or the "being used by another process" message) **or** a cloud-file error (the `ERROR_CLOUD_FILE_*` family, Win32 358–405 / message contains "cloud file" — e.g. a OneDrive files-on-demand placeholder a session-0 service can't hydrate): either ⇒ logged as a **Warning** + counted as `BackupResult.Warnings` (the file is skipped this run, temp cleaned), with the `reason` in the line; any other copy failure ⇒ logged Error + counted as `Errors`. Either way the rest of the pair continues. **Include/exclude filtering** lives here too: `WildcardMatcher` (static, over the BCL `FileSystemName.MatchesSimpleExpression` — `*`/`?`, case-insensitive, no dependency) and `BackupFilter` (built from a parent's filter rows projected to `FilterRule(FilterDirection, FilterKind, string Pattern)`). **File/Folder matching is name-only** (matched in every sub-folder); **exclude-`Path` matching is by exact relative location**: `IncludesFile` (empty include list ⇒ all files, else the name must match an include), `ExcludesFolder` (a folder-name match skips the subtree), `ExcludesPath(relativeSegments)` (true when the joined relative path equals an exclude-path rule or sits beneath one — that file, or that folder and its subtree; normalised, case-insensitive), `IsFileInScope(name, ancestorFolderNames)` (now also applies `ExcludesPath` to `ancestors + name`) and `IsRelativePathInScope(relPath)` (splits a flat zip path). The folder-pair sync engine threads a `BackupFilter` through its recursion (filtering the copy loop, leaving out-of-scope target files/folders undeleted, and not recursing folders excluded by name *or* by path); the archive engine passes `IsRelativePathInScope` as `CreateZipFromDirectory`'s `includeEntry` predicate.
- `Logging/` — operation logging via a factory. **Detail lines are stored in per-log files, not database rows** — `IOperationLogFileStore`/`OperationLogFileStore` (singleton, rooted at `{data dir}\operation-logs`) owns them: `AppendAsync(logId, level, messages)` writes one `[Level][yyyy-MM-dd HH:mm:ss] message` line per message to `{logId}.log` (serialised per log id by a `SemaphoreSlim`; a message with embedded newlines is written verbatim so its extra physical lines have no prefix), `ReadAsync(logId)` parses the file back into `OperationLogLine` records (a physical line without a recognised prefix is a continuation of the previous line's message — restoring embedded-newline messages), `ContainsAsync` scans for the Include-Messages filter, `ReadTailAsync(logId, maxLines)` streams just the **most recent** `maxLines` lines (memory-bounded, for the live terminal tailing a still-growing log; a thin wrapper over `ReadWindowAsync`), `ReadWindowAsync(logId, skip?, take)` returns a bounded window **plus** the file's total line count and per-level Warning/Error counts on the same streaming pass (null `skip` = the tail; a set one = lines [skip, skip+take) — the Logs terminal's expand/walk-back read), `SearchAsync(logId, text?, levels?, maxMatches)` is a **streaming grep** (case-insensitive `Contains` + optional level set, counts every match but returns at most `maxMatches` lines), and `Delete`/`DeleteAll` remove files. Tail/window/search all ride one shared `ParseStreamAsync` `IAsyncEnumerable` parser, so a huge log never materialises fully in memory. **Every read and write opens the file with `FileShare.ReadWrite | FileShare.Delete`** — a live tail-read (the View Progress dialog / an expanded terminal) must be able to coexist with the running backup's append; the default `File.Read*/Append*` helpers open with `FileShare.Read`, which made the *backup* fail with "being used by another process" while a terminal had the file open. Writes are still serialised per log id by the semaphore — the permissive share only lets a concurrent reader coexist. `IOperationLogFactory`/`OperationLogFactory` (singleton, DB-factory + file store) — `CreateAsync(name, level = OperationLogLevel.Info, profileId = null)` inserts a new `OperationLog` header row (the `level` here is the **starting/floor** header level — it applies to a line-less log and is then raised by the lines; `profileId` optionally ties the log to a profile so it cascade-deletes with it) and returns an `IOperationLogger` (impl `OperationLogger`) holding that row's id and the current header level. The logger appends lines **to the file** via `AppendAsync(params string[] messages)` (Info) / `AppendAsync(OperationLogLevel level, params string[] messages)` / `ErrorAsync(message, exception?)` (Error) — **one line per message** (pass several in a single call to write several lines rather than one delimited string); **each line carries its own `Level`**, and `ErrorAsync` appends the exception's `Message` only (no stack trace) to the message. **The header row is only touched when it must change** — once on the **first write** (to record the `LogFile` reference), and thereafter only when a line escalates the level — so a run's many lines cost file appends, not DB writes. **The header `Level` is kept in step as the most severe line seen** — Debug/Info → Info, any Warning → Warning, any Error → Error; the header only rises. The header message is **revised in place** via `SetSummaryAsync(message, level)` (updates `OperationLog.Name`, no extra record) — used to turn a "started…" title into a final "succeeded/failed in {duration}" summary so a run is a **single** log event (see `OneWaySyncHandler`); its `level` is a **floor** that can raise the header (e.g. force Error on a run that failed before logging an error line) but never lowers a level the lines already escalated to. The runtime logger type is `OperationLogger`, deliberately distinct from the `OperationLog` entity (and the enum is `OperationLogLevel`, not `LogLevel`, to avoid the `Microsoft.Extensions.Logging` clash). **`DeferredOperationLogger`** is an `IOperationLogger` wrapper that defers `IOperationLogFactory.CreateAsync` until the first line is actually written, so a unit of work that ends up doing nothing leaves **no** log row (`WasCreated` reports whether anything was written; `SetSummaryAsync` is a no-op until then). Used by the instant-sync watcher to suppress empty per-flush logs. The **read** side is `IOperationLogService`/`OperationLogService` (singleton, DB-factory): `GetPageAsync(page, size, filter?, includeMessages?, level?, profileId?)` → `PagedResult<OperationLog>` headers newest-first (`OrderByDescending(Id)` — SQLite can't `ORDER BY` a `DateTimeOffset`, each with its `Profile` `Include`d), optionally filtered by name via `EF.Functions.Like`, by exact `Level`, and by exact `ProfileId` (all AND-combined) — and, when `includeMessages`, an in-memory branch that also keeps a log whose **file** contains the text (`IOperationLogFileStore.ContainsAsync`); `GetDetailsAsync(logId)` → that log's `OperationLogLine` list read from its file (in file/write order — no `Sequence` any more); `GetRecentDetailsAsync(logId, maxLines)` → the memory-bounded tail (via `ReadTailAsync`), used by `LogTerminal`; `GetDetailWindowAsync(logId, skip?, take)` / `SearchDetailsAsync(logId, text?, levels?, maxMatches)` → the window/search pass-throughs the Logs terminal browses huge logs with (see the Logs bullet). Consumed by the Logs section (`Components/Pages/BackupServicePage/Logs.razor`). **History:** the legacy `OperationLogDetails` rows were copied into files by a one-time runtime migrator (since removed) that also dropped the table; the `AddOperationLogFile` migration adds the `LogFile` column and the later `DropOperationLogDetails` migration removes the table (`DROP TABLE IF EXISTS`, a no-op on already-migrated databases, so a fresh install's schema still ends up without it). **Push notifications:** `ILogWatcher`/`LogWatcher` (singleton) lets views refresh on a change rather than by polling — `OperationLogFactory`/`OperationLogger` call `logWatcher.Notify()` after **every** successful write (header create, line append, summary rewrite; the watcher is an optional ctor dependency, so test-constructed factories/loggers without it are a no-op). `Notify()` is **coalesced/debounced** (a single timer, `DebounceMilliseconds` = **1000 ms**): a burst raises **at most one** `Changed` per window, and because the window is **not** re-armed by later writes while one is already pending, a long continuous run still fires `Changed` ~once per window instead of going silent until it stops. `Changed` is raised on a background thread and invokes each subscriber in isolation (a throwing handler can't break the others). **The Logs page no longer subscribes** (it is static — see the Logs bullet); the live subscribers are the **`LogTerminal`** control (the View Progress dialog's tail) and the **Dashboard**, each subscribing in `OnAfterRender(firstRender)` and unsubscribing in `Dispose` (so closing the dialog / leaving the section stops the pushes). **Retention/purge:** `ILogRetentionService`/`LogRetentionService` (singleton; The run **unwinds cleanly leaving no temp files** — `OneWaySyncSynchronizer` threads the token into the crash-safe copy (`CopyToAsync(…, ct)`) and its `catch (OperationCanceledException)` deletes the partial `.tmp` before rethrowing, so a Stop mid-large-file is prompt and clean.   - **`IProfileStatusService`/`ProfileStatusService`** (singleton) — the **in-memory** run-status tracker for profiles (`ProfileStatus` Idle/Running/Error), backed by a `ConcurrentDictionary` (mutated by the background runner, read by the UI). `Get(id)` (defaults to `Idle` for unknown ids), `Set(id, status)` (raises the `event Action<int>? Changed` with the profile id), `Remove(id)`. It also tracks a per-profile **progress percent**: `SetProgress(id, percent)` (clamps 0–100, raises a **separate** `event Action<int>? ProgressChanged` only when the integer value changes — so a run pushes ~100 cheap updates, not a flood) and `GetProgress(id)` (null when not running/known); `Set` to a non-Running status clears the percent. Alongside the bare percent there is a richer **`ProfileProgress` snapshot** (`Profiles/ProfileProgress.cs` — `TotalPercent`, `StepName`, `StepPercent`, `StepCount`, `CurrentFile`): `SetProgress(id, ProfileProgress)` / `GetProgressDetail(id)`, raised on the same `ProgressChanged` only when the snapshot actually changes and likewise cleared when the run leaves `Running`. The engines thread the **current file name** into it (`OneWaySyncSynchronizer`/`ArchiveSyncProcessor` report the file being copied via the progress reporter); it's consumed by the on-screen progress window (`WindowsProgressWindowService`) and `ViewProgressDialog`. The grid shows **"Running - {percent}%"** in the Status cell and subscribes to `ProgressChanged` to re-render **just the cell** (`InvokeAsync(StateHasChanged)`, no DB reload) — distinct from `Changed`, which reloads the page on a status transition. The percent is **file-count based** for OneWaySync/InstantSync runs: each handler pre-counts work via `IOneWaySyncSynchronizer.CountFilesAsync` (a cheap source-only walk applying the same include/exclude + IncludeSubFolders scoping) and threads a `ProfileProgressReporter` (`IProgress<int>`) into `SyncAsync`, which reports `1` per in-scope file handled; ArchiveSync reports **per-item, sub-divided**: each item is an equal slice of the run, and within a slice the processor reports a 0..1 completion fraction where the first **75%** tracks files added to the zip (via a per-entry `onEntryProcessed` callback on `IBackupFileSystem.CreateZipFromDirectory`, against a pre-count of in-scope files) and the final **25%** tracks bytes copied to the target (a manual buffered copy in `CopyThroughTempAsync`); the handler maps `(itemIndex + fraction) × 100 / totalItems` to the percent via a synchronous `IProgress<double>`. Progress is never persisted (cleared when the run leaves Running). It also tracks a per-profile **lock** (`Lock`/`Unlock`/`IsLocked`, a separate set) used to mark a profile that's open in an edit/delete dialog — `BackupRunner` skips a locked profile so a scheduled run can't fire mid-edit; `Remove` clears the lock too. The status is also the **single-instance gate**: `IsRunning(id)` and the atomic `TryBeginRun(id)` enforce **one run per profile at a time** — the scheduler pre-checks `IsRunning` so it won't even spawn a thread, and `BackupRunner` calls `TryBeginRun` as the authority. **The gate is a separate active-runs set, not the displayed status**: `TryBeginRun` claims the profile in that set (and shows Running), and only **`EndRun(id, finalStatus)`** — called by `BackupRunner` when the run has fully unwound — releases it and sets the final status. So a handler that shows `Error` mid-run (its catch-all) doesn't let a second run start while the first is still unwinding. `Remove` clears it too. Status is **never persisted** — on startup `Program.cs` seeds every existing profile to `Idle`. The `Profiles` grid (`@rendermode InteractiveServer`) subscribes to `Changed` in `OnInitialized` and, when the changed profile is on the current page, **reloads the page data** (`InvokeAsync(async () => { await LoadAsync(_page); StateHasChanged(); })`) so the live Status cell *and* the entity-sourced columns it doesn't track (notably `DateLastRun`, which the runner writes in the DB) both refresh as a backup runs (`IDisposable` unsubscribes). The transitions are driven by the scheduler: `BackupRunner` sets `Running` then `Idle`, and `OneWaySyncHandler`'s catch-all sets `Error` (see `Scheduling/`).

- `Connections/` — **remote-resource connections** (an extensible `ConnectionType`; **SMB**, **Google Drive** and **USB** so far). A `Connection` (table) has `Name`, `ConnectionType Type`, `DateCreated` and a **1:1 child** `SmbConnectionSettings` (`Database/`, keyed by `ConnectionId`, cascade-deleted; `Host`/`Port`/`ShareName`/`Domain?`/`Username`/`PasswordEncrypted`/`RootFolder`). **The SMB password is encrypted at rest** (not hashed — SMB needs the plaintext to authenticate): `Security/ISecretProtector`/`DataProtectionSecretProtector` wraps **ASP.NET Core Data Protection** (`IDataProtectionProvider`, part of the Web SDK shared framework — no extra package; **cross-platform**, Windows + Linux). `Program.cs` registers `AddDataProtection().PersistKeysToFileSystem({DataDir}/keys).SetApplicationName("BackupService")` so the key ring lives next to the DB (`BackupDatabaseLocation.GetDataDirectory()`) and protected secrets stay decryptable across restarts. When the built-in client isn't configured the editor falls back to Advanced-only. Drive allows same-named siblings, which a name-path can't tell apart, so a **duplicate name (ignoring case) fails that folder's listing** — and any lookup that matches more than one item — with an error naming it, rather than backing one item up twice and the other never; items named `.`/`..` are left out (they'd escape a local target folder) (`MappableChildren`). A download that times out is reported as an error, not as a Stop; `OpenRead` downloads to a self-deleting local temp (and refuses a download that failed — Drive's media downloader reports failure through its returned progress rather than throwing — or came back shorter than the file's size, re-reading the size once in case the cached one is stale; `EnsureCompleteDownload`, unit-tested). A **Google Workspace file** (`application/vnd.google-apps.*` — Docs, Sheets, Slides, a shortcut; `NonDownloadableKind`) has no downloadable content, so `OpenRead` throws `FileNotDownloadableException` before any request and the engines skip it as a counted **Warning** every run (it isn't backed up — exporting is not implemented). Before this, such files were silently copied as 0-byte files that later runs skipped as unchanged, so a Drive-source backup may still hold those empty copies. **Workspace files are also protected from deletion and overwrite** — the app never creates one, so any on Drive is the user's own: `DeleteFile`, `OpenWrite` over an existing one, `MoveFile(…, overwrite: true)` onto one, and `DeleteDirectory` of a folder whose subtree holds one all throw **`ProtectedFileException`** (`ProtectedReason`, unit-tested), which OneWaySync/TwoWaySync/LightroomArchive catch and log as a counted **Warning** (`Kept '…' — …`) — so e.g. deleting an empty copy in a TwoWaySync profile no longer propagates to (and deletes) the real Doc, and a OneWaySync mirror to Drive no longer deletes Docs sitting in its target folder. (OneWaySync's orphan-folder delete also leaves a folder in place when anything inside was kept or couldn't be deleted, rather than also failing the folder delete — on Drive that delete would take the leftovers with it.) `OpenWrite` buffers to a local temp and uploads on close, `GetTempFilePath`/`CreateZipFromDirectory` throw `NotSupportedException` (local-only, exactly like SMB), and `GetZipComment` ranged-reads the EOCD tail. **Drive's `modifiedTime` is only millisecond-precise** (which would make the engine's exact write-time compare re-copy every run), so `SetLastWriteTimeUtc` also stores the source's exact tick count in a private `appProperties` entry that `GetLastWriteTimeUtc` reads back — a round-tripped timestamp is exact. The stamp is trusted only while Drive's own `modifiedTime` still agrees with it (within 1 ms): appProperties survive later revisions, so after someone edits the file in Drive the newer `modifiedTime` wins (`ParseWriteTime`) — otherwise the edit would be hidden and a two-way sync could overwrite it. **A refresh token works only with the OAuth client that issued it**, so the editor's model records which client the stored authorization (`StoredAuthClient`) and any token captured this session (`CapturedAuthClient`) belong to: switching between built-in and custom, or changing the custom Client ID, shows "Not authorized for this OAuth client" and Save requires a fresh Authorize; a captured token is only sent for the client it came from, and a blank secret box keeps the stored secret only for that same custom client (`CanKeepStoredSecret`). `ConnectionService.UpdateAsync` enforces the same two rules (throws). Authorize is cancellable (the button reads "Waiting for Google… (cancel)"; closing the dialog cancels too, dropping the pending attempt that holds the secret), and Browse/Test/Authorize report undecryptable stored secrets instead of crashing the page (as do the SMB editor and `ConnectionLocationField`). - `Scheduling/ScheduledTasks/` — the scheduled-task **scheduler, runner and process seam**. **`IScheduledTaskScheduler`/`ScheduledTaskSchedulerService`** mirrors `BackupSchedulerService` (BackgroundService in the same **three-role** registration: singleton, `IScheduledTaskScheduler`, hosted service; in-memory entries, `SemaphoreSlim` wake, `SyncAsync(taskId)`, persists `ScheduledTask.DateNextRun` via `ExecuteUpdateAsync`, startup load + missed-run catch-up) — **reusing** the public statics `BackupSchedulerService.GetNextOccurrence`/`ShouldCatchUp` rather than duplicating cron logic. A **Command** step runs the executable directly, or — when `RunViaShell` — wrapped in `cmd.exe /s /c "…"` on Windows (the `/s` form strips exactly the outer quote pair, so a quoted program path plus a quoted argument survive) or `/bin/sh -c …` elsewhere (`OperatingSystem.IsWindows()`, cross-platform, no `[SupportedOSPlatform]`). **A step is finished only when its program *and everything it started* have exited** (so a launcher that hands its work to a helper can't let the next step start early): on Windows every step runs inside a **Job Object** (`WindowsJobObject` — `KILL_ON_JOB_CLOSE`, P/Invoke, no package) which the runner waits to empty, and which **Stop** (`TerminateJobObject`) or the app exiting/crashing (the handle closing) kills in full — even a background program whose launcher has already exited. A step that starts a long-running server therefore keeps the task Running until stopped. Off Windows the step ends when its output closes (a background program inherits it), and Stop reaches the process tree only while the step's own program runs. A **PowerShell** step writes its `Script` to a temporary `.ps1` (UTF-8 BOM) and runs it via `pwsh -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <temp>` when `pwsh` is on `PATH`, else Windows `powershell` (the temp file is deleted in a `finally`). Either way it streams stdout/stderr to completion, honours the token (kills the process tree on cancel), and returns `ProcessRunResult(ExitCode, StandardOutput, StandardError)`. The runner is unit-tested against a fake `IProcessRunner` in `ScheduledTaskRunnerTests` (order, stop-on-failure, stdout/stderr capture, BackupRun recording, `[Manual]` prefix, cancellation → warning/idle).

- `Options/` + `Notifications/` + `Hosting/IStartupManager` — the **Settings → Options** desktop-integration toggles. The single-row **`AppOptions`** table (`Database/`, like `LogRetentionSettings`; `StartWithWindows`/`ShowTrayIcon`/`AllowNotifications`, all default **false**) is owned by **`Options/IAppOptionsService`/`AppOptionsService`** (singleton, DB factory; lazy-seed + `UpdateSettingsAsync` + a `Changed` event). `OptionsPanel` (`Components/Pages/Options/`) edits the three via themed `ToggleButton`s; **Save** persists, calls `IStartupManager.Apply(startWithWindows)`, and toasts. `ShowTrayIcon`/`AllowNotifications` are **Windows-only**; off Windows those two settings persist but no-op. **Autostart** (`StartWithWindows`) works on **Windows and Linux** — `Hosting/IStartupManager` (`WindowsStartupManager` writes/removes the per-user `HKCU\…\Run\BackupService` value = `"{exe}" -background`, using `Microsoft.Win32.Registry` which the net10.0 framework already provides — no package; `LinuxStartupManager` writes/removes an XDG autostart entry at `~/.config/autostart/backupservice.desktop` whose `Exec=` launches the plain foreground exe with no arguments — since the `-background`/`-stop` process-control model is Windows-only, see `Hosting/BackgroundProcessManager` — the desktop session keeps it running detached from any terminal; `NoopStartupManager` elsewhere, e.g. macOS). `Program.cs` reconciles the autostart entry with the saved option at startup so the registered path tracks the exe after a redeploy. **Tray icon + notifications** — `Notifications/WindowsTrayService` (Windows-only, registered in the three-role pattern: singleton + `IDesktopNotifier` + hosted service) runs a Win32 message loop on a dedicated STA thread with a hidden top-level window and a `Shell_NotifyIcon` tray icon (double-click opens the admin UI; a right-click menu offers Open / Exit via `IHostApplicationLifetime`). The icon is present when `ShowTrayIcon` **or** `AllowNotifications` is on (a balloon attaches to a tray icon); it caches the options and refreshes via `IAppOptionsService.Changed`. **`IDesktopNotifier`** (`NotifyBackupCompleted`/`NotifyTaskCompleted` + `NotifyDeviceConnected`/`NotifyDeviceDisconnected`; `NullDesktopNotifier` off Windows) shows a balloon (`NIF_INFO`, severity-coloured by `RunOutcome` for runs) — for a **discrete** run completion (`NotifyBackupCompleted`) and **start** (`NotifyBackupStarted`) it's hooked as an **optional** trailing `IDesktopNotifier? notifier = null` ctor param on the four backup handlers (`OneWaySyncHandler`/`ArchiveSyncHandler`/`InstantSyncHandler`/`LightroomArchiveHandler` — start at the top of `HandleAsync`, completion in the `finally` after the run summary, skipped when cancelled) and `ScheduledTaskRunner`. **Each backup run also honours the profile's own notification settings** (`Profile.NotificationsEnabled`/`NotifyOnStart`/`NotifyOnComplete`): a handler fires the start balloon only when `NotificationsEnabled && NotifyOnStart`, and the completion balloon only when `NotificationsEnabled && NotifyOnComplete` (all still under the global `AllowNotifications` gate); the continuous InstantSync/Lightroom **watcher flushes are deliberately not hooked** (too noisy); the device methods are called by `UsbDeviceWatcherService` on connect/disconnect. All balloons are gated by the `AllowNotifications` option. **On-screen progress windows** are a separate Windows-only feature: `Notifications/WindowsProgressWindowService` (registered as a hosted service in the Windows block) runs its own message-loop thread (like `WindowsTrayService`) and, for any profile with `Profile.ShowProgressWindow`, draws a small borderless always-on-top GDI window in the bottom-right showing the profile name, action and a progress bar; multiple running profiles **stack vertically**. It's driven entirely by `IProfileStatusService` (`Changed` → show/hide as a profile enters/leaves Running, looking up the profile's name/type/flag from the DB; `ProgressChanged` → repaint the bar) and is independent of the `AllowNotifications` balloon gate. **Future (not built):** the autostart could be surfaced per-machine vs per-user.
- **Auth model:** cookie authentication for a **single admin account** (username `admin`, default password `admin`, stored **hashed** in the `AdminCredentials` table — a future change will allow editing it). Session uses a **30-minute sliding (inactivity) expiry**. Every page requires authentication via `@attribute [Authorize]` in `Components/Pages/_Imports.razor` (applies to all pages there); the login page opts out with `@attribute [AllowAnonymous]`. Enforcement is by `AuthorizeRouteView` in `Routes.razor`, **not** a global authorization `FallbackPolicy` — a fallback policy is enforced at the Blazor endpoint level and would also block `/login`, causing a redirect loop. `Login.razor` is a **static SSR** page (no interactive render mode) so its form POST is a real HTTP request that can write the auth cookie via the cascaded `HttpContext`.
- Configuration comes from `appsettings.json` plus an environment-specific overlay (`appsettings.Development.json` / `appsettings.Production.json`), selected by `ASPNETCORE_ENVIRONMENT` (set to `Development` in `Properties/launchSettings.json`; unset → Production for the deployed service).
- User secrets are enabled (`UserSecretsId` in the csproj) — use `dotnet user-secrets` for local credentials rather than committing them.

## Conventions

- `Nullable` and `ImplicitUsings` are enabled — common namespaces (e.g. `Microsoft.Extensions.Logging`, `System.Threading`) are available without explicit `using` statements.
- **Workstation GC, deliberately** (`<ServerGarbageCollection>false</ServerGarbageCollection>` in the csproj, overriding the Web SDK's Server-GC default). Server GC keeps per-core heaps and holds freed memory rather than returning it to the OS — on a many-core machine this single-user localhost app sat at a 1GB+ Task Manager working set with no leak. Workstation GC returns memory eagerly and the throughput difference is irrelevant here; don't flip it back, and don't add `GC.Collect()` calls to component `Dispose` methods to fight the working set (they were tried and removed — under Server GC they didn't shrink it anyway).
- The project uses C# primary constructors (see `Worker(ILogger<Worker> logger)`); follow that style for new injected services.
- **Enums live in `BackupService/Enumerations/`** (namespace `BackupService.Enumerations`), one enum per file named after the enum (e.g. `ProfileStatus.cs`). Do not declare enums alongside the entity/component that uses them. The namespace is brought in via `@using BackupService.Enumerations` in `Components/_Imports.razor` for the component tree, and an explicit `using BackupService.Enumerations;` in non-Razor files that reference an enum.
- **Extension methods live in `BackupService/Extensions/`** (namespace `BackupService.Extensions`), e.g. `EnumExtensions.GetDescription(this Enum)` which returns a value's `[Description(...)]` text (falling back to the name). Give enum values shown in the UI a `[Description]` and render `value.GetDescription()` rather than the raw name. There is also a project-local `[HelpText("…")]` attribute (`Extensions/HelpTextAttribute.cs`) read by `EnumExtensions.GetHelpText(this Enum)` (returns the text, or empty string if absent) — used for the longer explanatory blurb shown under a dropdown (e.g. `OverwriteBehaviour`). The namespace is imported in `Components/_Imports.razor`. (Note: in the test project NUnit's global `using NUnit.Framework` makes `Description` ambiguous with `System.ComponentModel.DescriptionAttribute` — fully-qualify it there.)
- **Blazor components use code-behind.** A `.razor` file should hold only markup and the minimal C# unavoidable in markup (e.g. simple `@bind`/event wiring); put the bulk of the logic — fields, properties, lifecycle methods, event handlers, `[Inject]` services — in a sibling `.razor.cs` partial class (`public partial class Foo { ... }` in the component's namespace). Create the code-behind whenever a component needs more than trivial inline code.
- **Each page gets its own folder under `Components/Pages/`.** A routable page lives in `Components/Pages/<PageName>/<PageName>.razor`, with its code-behind and any page-specific files (sub-components, view models, partials) in that same folder. Examples: `Components/Pages/Dashboard/`, `Components/Pages/Settings/`, `Components/Pages/Authentication/` (the Login page). The folder becomes part of the component namespace (e.g. `BackupService.Components.Pages.Authentication`); match the code-behind's `namespace` to it. Routes come from `@page`, not the folder, so moving a page between folders doesn't change its URL. (Note: the page folder `Components/Pages/Authentication/` is distinct from the root `Authentication/` folder, which holds the auth *services*.)
- **For logging, use `Microsoft.Extensions.Logging`** — inject `ILogger<T>` via the constructor (already configured by the host; no third-party logging framework like Serilog or NLog). Use structured-logging message templates (e.g. `logger.LogInformation("Backed up {File}", path)`).
- **Use dependency injection throughout, via the built-in `Microsoft.Extensions.DependencyInjection` container** (available as `builder.Services` — no third-party container like Autofac). Register services on `builder.Services` (`AddSingleton`/`AddScoped`/`AddTransient`) and inject them via constructors rather than newing them up or using static/singleton access. Backup logic should live in injectable services (interface + implementation) consumed by `Worker`, not inline in `Worker` itself.

Three flavours: a plain `dotnet build`/`run` bakes **`0.0.0-dev`** (the csproj default `VersionPrefix`/`VersionSuffix`); the **`Install` publish profile** bakes **`0.0.{buildnumber.txt}-published`** — its `SetPublishedVersion` target reads `buildnumber.txt` (the local build-number source) and sets `Version`/`InformationalVersion` **before compile** (`BeforeTargets="GetAssemblyVersion"`), and `PersistPublishedBuildNumber` increments the file once after publish; **CI** (`.github/workflows/build.yml`) bakes **`{Major}.{Minor}.{build}`** by reading Major/Minor from appsettings (jq) and passing `-p:Version={Major}.{Minor}.{github.run_number}`. `IncludeSourceRevisionInInformationalVersion` is off so there's no `+<sha>` suffix. `buildnumber.txt` is now **build-time only** (no longer copied to output / read at runtime).
